# Задача: разработать полностью локальное Android-приложение для системной DPI-десинхронизации без root

Ты выступаешь как ведущий Android-разработчик, сетевой инженер, Rust/C-разработчик, специалист по Android `VpnService`, TUN/TCP/UDP-проксированию и сборке нативных Android-компонентов через Android NDK.

Не ограничивайся созданием документации или прототипа. Необходимо последовательно спроектировать, реализовать, протестировать и скомпилировать рабочее Android-приложение.

## 1. Основная цель

Создай красивое, простое и понятное Android-приложение, которое:

- работает полностью без root;
- не требует удалённого сервера;
- не изменяет внешний IP-адрес пользователя;
- не является классическим VPN-сервисом с удалённым VPN-сервером;
- использует Android `VpnService` для локального перехвата системного трафика;
- проксирует трафик всех приложений или выбранных приложений;
- локально применяет DPI-десинхронизацию к HTTP, HTTPS/TLS и частично QUIC;
- использует TUN-интерфейс и локальный userspace-прокси;
- работает на Wi-Fi и мобильной сети;
- поддерживает IPv4, а после стабилизации — IPv6;
- сохраняет настройки между перезапусками;
- предоставляет понятные профили вместо сложных консольных аргументов.

Рабочее название приложения:

`Zapret Mobile`

Название должно быть вынесено в ресурсы и легко заменяться.

## 2. Критическое техническое ограничение

Приложение не должно требовать:

- root;
- Magisk;
- `iptables`;
- `nftables`;
- NFQUEUE;
- `CAP_NET_ADMIN`;
- `CAP_NET_RAW`;
- собственного ядра Android;
- удалённого SOCKS/VPN-сервера.

Не пытайся запускать оригинальный `nfqws2`, поскольку без NFQUEUE он не сможет работать в штатном режиме.

Нужно создать rootless-реализацию применимых принципов Zapret/ByeDPI на уровне:

- Android `VpnService`;
- TUN;
- локального SOCKS5-прокси;
- userspace TCP/UDP relay;
- управления TLS-потоком;
- разделения отправляемых данных;
- анализа TLS ClientHello;
- анализа HTTP Host;
- управления UDP/443 и QUIC.

Нельзя заявлять полную совместимость с оригинальным Zapret2. В документации необходимо явно указать, какие методы поддерживаются полностью, частично или не поддерживаются без root.

## 7. Android VpnService

Реализуй собственный сервис:

`ZapretVpnService`

Он должен:

- запрашивать разрешение через `VpnService.prepare()`;
- создавать TUN-интерфейс;
- работать как foreground service;
- показывать постоянное уведомление;
- корректно обрабатывать остановку;
- восстанавливаться после смены Wi-Fi и мобильной сети;
- не создавать рекурсивную сетевую петлю;
- защищать исходящие сокеты через `VpnService.protect()`;
- корректно закрывать TUN FD;
- не оставлять зависшие нативные процессы;
- поддерживать запуск и остановку из интерфейса;
- поддерживать системный Always-on VPN;
- корректно работать после удаления приложения из списка последних приложений.

Пример конфигурации:

```kotlin
val tun = Builder()
    .setSession("Zapret Mobile")
    .setMtu(1500)
    .addAddress("10.71.0.1", 24)
    .addRoute("0.0.0.0", 0)
    .addDnsServer("1.1.1.1")
    .establish()
```

После стабилизации IPv4 добавь:

```kotlin
.addAddress("fd71::1", 64)
.addRoute("::", 0)
```

Не копируй пример вслепую. Обработай исключения, `null`, отсутствие разрешения, повторный запуск и восстановление после аварии.

## 9. TUN-to-SOCKS

Для первого рабочего варианта используй:

`hev-socks5-tunnel`

или эквивалентный стабильный компонент.

Он должен:

- получать TUN file descriptor;
- направлять TCP в локальный SOCKS5-сервер;
- поддерживать UDP настолько, насколько это необходимо;
- работать только локально;
- корректно завершаться;
- не создавать утечки памяти;
- поддерживать IPv4;
- позже поддерживать IPv6;
- записывать диагностические события в общий лог.

Локальный адрес SOCKS5:

```text
127.0.0.1:1080
```

Порт должен быть динамически настраиваемым, чтобы исключить конфликт.

## 10. Локальный DPI-движок

Создай локальный SOCKS5-движок, условно:

`ZapretStream`

Он должен:

- принимать SOCKS5 CONNECT;
- определять конечный адрес;
- создавать исходящий сокет;
- передавать файловый дескриптор Android-части для вызова `VpnService.protect(fd)`;
- после защиты подключаться к конечному серверу;
- анализировать первые клиентские данные;
- определять HTTP, TLS и неизвестный протокол;
- применять выбранную стратегию;
- после начальной обработки работать как высокопроизводительный bidirectional relay;
- иметь таймауты;
- ограничивать размеры буферов;
- корректно обрабатывать half-close;
- не читать весь поток в память;
- поддерживать отмену;
- корректно завершать соединения при остановке VPN.

Используй неблокирующий ввод-вывод:

- Rust Tokio;
- `epoll`;
- или другой эффективный event loop.

Не создавай отдельный тяжёлый поток на каждое соединение без необходимости.

## 11. TLS ClientHello

Реализуй минимальный безопасный парсер TLS ClientHello.

Он должен определять:

- TLS record;
- handshake type;
- ClientHello;
- длины секций;
- extensions;
- SNI;
- ALPN;
- позицию начала SNI;
- позицию середины SNI;
- позицию конца SNI.

Парсер обязан:

- проверять все длины;
- не выходить за границы буфера;
- корректно обрабатывать фрагментированный ClientHello;
- иметь ограничение максимального размера;
- не доверять данным клиента;
- не падать на неизвестных extensions;
- иметь unit-тесты на повреждённые данные.

Не расшифровывай HTTPS и не устанавливай собственный CA-сертификат.

Приложение не должно выполнять TLS MITM.

## 13. Стратегии десинхронизации

Для MVP реализуй следующие действия:

### TLS/HTTP split

- разделение перед SNI;
- разделение в начале SNI;
- разделение в середине SNI;
- разделение после SNI;
- разделение после первого байта;
- пользовательская числовая позиция;
- несколько последовательных разделений.

### Отправка

- отдельные `write()` для частей;
- `TCP_NODELAY`;
- регулируемая задержка между частями;
- немедленная отправка;
- случайная задержка в ограниченном диапазоне;
- ограничение максимальной задержки.

### TLS record fragmentation

Реализуй создание нескольких корректных TLS records из одного ClientHello там, где это технически возможно без нарушения TLS-сессии.

### HTTP Host manipulation

Поддержи безопасные потоковые методы:

- разбиение строки Host;
- разбиение заголовка;
- изменение порядка отправки частей без изменения содержимого запроса.

Не изменяй фактическое имя домена, если это ломает TLS или HTTP.

### QUIC

Для первой версии:

- обнаруживай UDP/443;
- предоставь настройку «Отключать QUIC»;
- при включении блокируй UDP/443;
- позволяй приложениям переходить на HTTPS через TCP/443.

Позже добавь экспериментальный UDP relay и анализ QUIC Initial.

### Fallback

Если соединение:

- сброшено;
- не установилось;
- завершилось по таймауту;
- закрылось до получения ответа,

движок может повторить соединение с другой стратегией, но только если повтор безопасен.

Не повторяй автоматически потенциально неидемпотентные HTTP-запросы после передачи тела запроса.

## 30. Ограничения, которые нужно честно описать

Создай `docs/LIMITATIONS.md`.

Обязательно укажи:

- приложение занимает системный VPN-слот;
- одновременно нельзя использовать обычный `VpnService`, WARP, WireGuard или AdGuard VPN;
- приложение не реализует NFQUEUE;
- приложение не является полной копией Zapret2;
- raw packet strategies недоступны;
- произвольный TCP SEQ/ACK недоступен;
- `badsum`, `md5sig`, полноценный `seqovl` недоступны;
- поведение зависит от оператора, сети и DPI;
- некоторые приложения могут не выполнять fallback с QUIC на TCP;
- некоторые приложения могут использовать собственный сетевой стек;
- Always-on VPN может влиять на доступ в сеть при ошибке сервиса;
- батарея может расходоваться быстрее;
- OEM-прошивки могут ограничивать foreground service.
